# Measured remediation — release still blocked

> Historical Phase 19 evidence. See [PR #1 remediation](pr1-remediation.md) for the subsequent implementation and remeasurement.

The SC-012 reference exposes a real bottleneck. Initial three-warmup/ten-trial medians were 2345.77 ms per 30 rush ticks and 5865.65 ms per active shaft edit. A separate Node CPU profile of exactly 30 ticks took 2542.71 ms, dominated by `clonePlain` and recursive `assertPlain` descriptor inspection. See [before reports](phase-19-before/) and the runnable `node scripts/profile-reference.mjs` profiler.

Changed `src/simulation/core/clock/advance.ts`: public advancement and runner creation still validate input. Each owned event boundary now makes its detached rollback draft using direct JSON copying of that already validated state, avoiding duplicate descriptor inspection. Failure still leaves the last completed boundary intact. New `tests/integration/owned-runner.test.ts` verifies public/owned equivalence, previous-boundary non-aliasing, malformed input rejection, overflow rollback and diagnostic-counter neutrality. Existing active-phase, three-day and full-cohort congestion tests are retained.

The after CPU profile took **972.46 ms**, with whole-state JSON copying and event-heap rebuilds now dominant. The final restored-trial reference rush median/p95 is **867.09 / 890.22 ms per 30 ticks**, about **34.6 ticks/real second**. The reference active edit median/p95 remains **5669.44 / 5714.08 ms**. These fail the required 120/480/960 rates and 150 ms response budget. No browser FPS qualification follows from these Node measurements.

`tests/benchmarks/scaling.bench.ts` also moved full-population sampling into a separate untimed replay; initial dense-walking/dormant timings measured observer scans and are explicitly superseded. Before/after timings therefore include a harness correction; the separately collected CPU profiles substantiate the validation optimization. Every shared before/after workload retains the same fixture/final-state digests. Optional work counters in `src/simulation/core/work-counters.ts` and graph/search/cache/event call sites expose remaining work without adding persistent state or changing decisions.

Remaining measured work includes whole-population rollback copies at event boundaries, reconstruction of event heaps from replaced arrays, and per-traveler route/topology work during edits. Resolving these safely needs further correctness-preserving implementation and identical-fixture remeasurement. No performance gate is waived; T152 stays unchecked. Workers, ECS, incremental graphs, LOD, changed demand, bigger cars and weakened assertions were not introduced.

A native 76.9-second Firefox probe then exposed an application pacing problem: `GameSession.frame` waited until after each 32-tick batch to check its approximately 4 ms work budget. The event-heavy reference therefore rendered only around 1–2 FPS. `src/app/game/session.ts` now checks after each completed tick, preserving the 240-tick ceiling and all foreground debt. A new failing-before/passing-after `tests/unit/pacing.test.ts` case verifies that the injected budget cannot process 128 ticks before yielding when only four one-tick units fit. This does not alter authoritative ordering, movement, demand or headless benchmark digests. Follow-up native probe summaries are retained in `browser-results.json`; the full qualification remains open.

The post-fix native probe measured median 42.659 FPS (minimum 34.826) across 42 normal windows, versus median 1.495 in the earlier 56-window probe. Both start with the same reference seed/state; their 48.474/76.912-second durations and ending ticks differ. Median delivered simulation throughput remained only 43.011 ticks/second after the fix, with outstanding debt. This establishes improved yielding, not recovered target throughput or complete browser qualification.
